Developing a chatbot for our The Run of Play website (therunofplay.com).

Answers user football related queries using our football articles and if needed web searched knowledge in fun footballing manner.

Currently hosted on PythonAnywhere and utilised as an api using offthebar.pythonanywhere.com/api/chat.

## Architecture

- `run.py` — entrypoint. Loads `.env`/`.env.sh`, wires `server/website.py` (page routes) and `server/backend.py` (API routes) onto the Flask app from `server/app.py`.
- `server/app.py` — Flask app, CORS (open to all origins), `/` (redirects to `/chat/`), `/chat/` (renders the chat UI), `/api/chat` (the public conversation API). No login/auth gate — access is expected to be controlled by who is handed the chat link or an API credential, not by Google OAuth (removed).
- `server/backend.py` — `Backend_Api._conversation`: builds the system prompt, calls `ask_from_llm` to decide if fresh retrieval is needed, then streams a Gemini answer in two phases:
  - Phase 1: fast draft using whatever context is available, ends with a "HALFTIME" transition line shown to the user.
  - Phase 2: re-runs retrieval with `force_search=True` and streams a refinement continuing the draft (or `NO_NEW_UPDATES` if nothing new).
- `ragwithsearch.py` — retrieval core:
  - `classify_and_build_query` — Gemini (`gemini-2.5-flash-lite`) + heuristic keyword classifier decides `search_required` and builds a keyword-rich query; resolves follow-up pronouns using recent conversation history.
  - `build_news_context` (formerly `formatted_prompting`) — checks Pinecone KB first (`kb_google.search_pinecone`); if a match is fresh (score ≥ 0.7, ≤ 30 days old) uses only that context; otherwise falls back to web search via a self-hosted SearXNG instance (`SEARXNG_URL` env var, restricted to `engines=bing,bing news` — see below), scrapes top results with `crawl4AI.py`, and ranks chunks with BM25. Always returns `(context, search_required, formatted_query)`.
- `kb_google.py` — Pinecone-backed knowledge base. Embeddings via Hugging Face inference API (`BAAI/bge-small-en-v1.5` with fallbacks), index name `football-docs`. Exposes `embed_texts`/`get_pinecone_index` as public entry points (used by `ingest_kb.py`) alongside `search_pinecone` (used by the live retrieval path).
- `ingest_kb.py` — ingestion pipeline: pulls posts from the Wix blog's REST API (`GET https://www.wixapis.com/v3/posts`, `fieldsets=CONTENT_TEXT` for plain text), chunks each post, embeds via `kb_google.embed_texts`, and upserts into Pinecone via `kb_google.get_pinecone_index`. Meant to run periodically (see `PYTHONANYWHERE.md`), not as part of the request path.
- `prompt_templates.py` — system prompt (football-pundit persona, "controlled poetic flair" rules) and prompt builders for first draft / refinement / search classification.
- `gemini_utils.py` — round-robins across multiple Gemini API keys (`GEMINI_API_KEY`, `GEMINI_API_KEY_2`, ... or `GEMINI_API_KEYS`) per model call, using the `google.genai` SDK (`genai.Client`, not the deprecated `google.generativeai`). `call_gemini_with_key_retry()` wraps a Gemini call and automatically retries with the next rotated key on a quota-exceeded error (e.g. the free tier's 20-requests/day-per-model limit) — used by every Gemini call site instead of calling `build_gemini_client()` directly.
- `client/` — static frontend (`index.html`, `chat.js`, `style.css`).
- Config: `config.json` (host/port/proxy), `config_env.py` (`require_env` helper, loads `.env`), `.env.example` lists required secrets. See `PYTHONANYWHERE.md` for deployment layout (secrets kept outside the repo on the server filesystem).

## Future work
- `chat_storage.py`'s file writes are only guarded by an in-process `threading.Lock` — fine for the single-process dev server, but would not be safe if production ever runs multiple worker processes (e.g. gunicorn with >1 worker) writing the same conversation concurrently. Worth a file lock (e.g. `fcntl`) or a real datastore if that becomes true. Also no retention/cleanup policy yet on `chat_logs/` — it will grow unbounded.
- Re-test the "messi latest news" query live now that both the staleness-labeling fix and the `max_output_tokens` bump have landed together — confirmed each fix individually, not yet the combination in one real request.
- Check whether the current PythonAnywhere account (free vs paid, and its creation date relative to 2026-01-15) actually supports the task cadence wanted for `ingest_kb.py` before relying on it.
- No automated tests exist yet for the retrieval/classification logic (`ragwithsearch.py`) or the streaming backend (`server/backend.py`).
- The Gemini-call path has only been smoke-tested with a mocked `google.generativeai`; worth a real end-to-end check against `/api/chat` with real credentials before considering the backend fully unblocked.
- Web search now depends entirely on Bing being reachable from the SearXNG Cloud Run instance's IP (see below) — no fallback engine. If Bing ever starts CAPTCHA'ing/rate-limiting that IP the way DuckDuckGo/Google/Brave/Startpage already do, search breaks again with nothing to fall back to. The real fix at that point is routing SearXNG's outbound requests through a residential/rotating proxy, or switching to a paid search API (Bing Search API, Brave Search API, etc.) instead of scraping.
- `is_scraping_allowed` calls `RobotFileParser.read()` synchronously per candidate URL with no timeout — a slow/hanging `robots.txt` fetch would stall the whole retrieval path. Not hit in practice yet, but worth a timeout if it ever becomes a problem.
- Pinecone metadata dates aren't all the same format: `build_news_context`'s date parsing expects `%Y-%m-%dT%H:%M:%S.%fZ` (with fractional seconds) and logs a "Date parse error" for at least one real article whose `created` field is `2026-06-02T21:03:20Z` (no fractional seconds) — falls back gracefully (treated as "Unknown Date"/oldest-possible), doesn't crash, but the actual date for that article is silently lost. Pre-existing, unrelated to the google.genai migration below; noticed while verifying it. Worth a more lenient date parser (try multiple formats, or use `datetime.fromisoformat` with a fallback) if it turns out to affect more than a handful of ingested articles.

  - No relevance filtering before scraping: the code just walked SearXNG's result list top-to-bottom and scraped the first 2 whose `robots.txt` allowed it. Bing sometimes ranks tangentially-matched pages highly for ambiguous query terms (e.g. "Lionel Messi" surfacing "first name vs last name" grammar pages, or Lionel-brand model-train stores) — once the genuinely relevant results got skipped (robots.txt, no content), the loop fell through to scraping that junk.   - `rank_chunks_bm25` crashed with `ZeroDivisionError` (`BM25Okapi` dividing by an empty corpus) whenever a scraped page's text had no tokenizable sentences — happens for real, e.g. MSN article pages that `crawl4AI` logs as "Blocked by anti-bot protection... 0 chars visible" but that still pass the earlier `if not page_text` check (the string isn't empty, just not real content). This silently killed the entire request. Now skips the page instead of calling BM25 on an empty chunk list.
  - Also fixed a latent `KeyError` in `page_contents[ctx['url']]`: that dict was only populated from the first 10 raw results, but the new relevance filter can legitimately pick a result ranked below position 10. Now builds `page_contents` from the full result list and looks it up with `.get(..., '')` as a second safety net.

- Migrated off the deprecated `google.generativeai` SDK to `google.genai` (`requirements.txt`: `google-generativeai` → `google-genai`; confirmed by fully uninstalling the old package and re-testing - no hidden dependency remained). Key API differences that required real code changes, not just an import swap:
  - No more global `genai.configure(api_key=...)` + `genai.GenerativeModel(...)`. Each call now goes through a `genai.Client(api_key=...)` instance, and the model name is passed per-call (`client.models.generate_content_stream(model=..., contents=..., config=...)`) rather than being bound at model-construction time. `gemini_utils.build_gemini_model()` → `build_gemini_client()`, and `call_gemini_with_key_retry()`'s `call_fn` now receives a `Client` instead of a `GenerativeModel`.
  - `genai.GenerationConfig(...)` → `google.genai.types.GenerateContentConfig(...)` - same field names (`max_output_tokens`, `temperature`, `top_p`), but `safety_settings` now goes inside this same config object instead of being bound separately at model-construction time (plain dicts like `{"category": "HARM_CATEGORY_HARASSMENT", "threshold": "BLOCK_MEDIUM_AND_ABOVE"}` still work, confirmed - no need to construct `types.SafetySetting` objects).
  - No more `model.start_chat(history=...)` + `chat.send_message(...)`. Replaced with `client.models.generate_content_stream(model=..., contents=history + [new_turn], ...)` directly - the history-plus-new-message list is contents, no separate Chat object needed. This is a uniform pattern across all four call sites now (previously two used the Chat API, two called `generate_content` directly).
  - **Real, necessary content-format change, not cosmetic**: conversation turns must be `{"role": ..., "parts": [{"text": "..."}]}` - a bare string in `parts` (what the old SDK accepted leniently, and what this codebase's `gemini_conversation` list was already built with) raises a pydantic `ValidationError` under the new SDK. Fixed everywhere turns are built in `server/backend.py` (the main `gemini_conversation` list, the appended complete-context instruction turn, and the Phase 1 first-draft turn).
