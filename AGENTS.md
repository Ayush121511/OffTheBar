Developing a chatbot for our The Run of Play website (therunofplay.com).

Answers user football related queries using our football articles and if needed web searched knowledge in fun footballing manner.

Hosted on Google Cloud Run and used as an API via `https://offthebar-api-607277832880.asia-south1.run.app/api/chat` (the old PythonAnywhere host, `offthebar.pythonanywhere.com/api/chat`, is legacy - see Hosting below).

## Architecture

- `run.py` — entrypoint. Loads `.env`/`.env.sh`, wires `server/website.py` (page routes) and `server/backend.py` (API routes) onto the Flask app from `server/app.py`.
- `server/app.py` — Flask app, CORS (open to all origins), `/` (redirects to `/chat/`), `/chat/` (renders the chat UI), `/api/chat` (the public conversation API), `/api/warm` (called by the chat pages on load, held open until a cold instance has finished loading). No login/auth gate (Google OAuth was removed) and no API credential check or rate limit either — anyone who has the URL can call `/api/chat` or `/backend-api/v2/conversation`.
- `server/backend.py` — `Backend_Api._conversation`: builds the system prompt, calls `ask_from_llm` to decide if fresh retrieval is needed, then streams a Gemini answer in two phases. Every call passes the system prompt as Gemini's `system_instruction`; the contents are the chat history as sent, then one user turn from `prompt_templates.build_answer_turn` (retrieved context + question + that phase's instruction):
  - Path choice: if the classifier says no search is needed, one complete answer. Otherwise `ragwithsearch.judge_kb_coverage` (flash-lite) rates how much of the answer the Run of Play hits hold as of today: `full` -> one complete answer from them (no web search); `partial` -> Phase 1 + Phase 2 below; `none` -> no draft: the status line straight away, then one complete answer from the web search plus the Run of Play hits. Phase 1 can also reply `NO_RELEVANT_CONTEXT` (held back like `NO_NEW_UPDATES`), which switches to that same combined answer.
  - Status lines: retrieval runs inside the streamed response (`answer_stream`), and each stage streams a `## HALFTIME!!! <status>` line as it starts: "Searching The Run of Play" (classifier, Run of Play search, coverage check), "Searching the web" (only while the web search is still running when an answer needs it), "Generating" (until the first words of an answer, or of the update after a draft). The clients show only the latest status, while nothing follows it, as a grey shimmer line with a seconds counter that restarts for each stage, and strip every status line from the answer; they show "Searching The Run of Play" themselves the moment a message is sent (no more typing dots). Clients opt in with `stage_statuses: true` in the payload; without it (the live Wix page until the new code is published, or a tab opened before a publish) only the single status line older clients handle is sent, before the web update or the combined answer - they strip one status line and render any other as a "HALFTIME!!! ..." heading. Saved transcripts have no status lines. The `## HALFTIME!!!` prefix is the wire marker; changing it would make older embeds show the raw line.
  - Phase 1: fast draft using whatever context is available, then the web search's status and Phase 2.
  - Phase 2: the web search (`ask_from_llm(..., force_search=True)`) starts in a background thread (`WEB_PREFETCH_POOL`) as soon as the classifier wants a search, via `ask_from_llm`'s `on_search_planned` hook - alongside the Run of Play search, the coverage check and the draft - and Phase 2 (or the combined answer) takes its result. It goes unused when coverage is `full`. Phase 2 streams a refinement continuing the draft. If Gemini says `NO_NEW_UPDATES`, or there's no new context, the answer simply ends on the draft.
- `ragwithsearch.py` — retrieval core:
  - `classify_and_build_query` — Gemini (`gemini-2.5-flash-lite`) + heuristic keyword classifier decides `search_required` and builds a keyword-rich query; resolves follow-up pronouns using recent conversation history. Award/title questions without a year ("Who won the Ballon d'Or?") count as current.
  - `judge_kb_coverage` — flash-lite rates the Run of Play hits `full` / `partial` / `none` for the question as it stands today (`prompt_templates.build_relevance_check_prompt`); `partial` if the check fails. For a latest-news question with no Run of Play hit from the last 14 days (`LATEST_NEWS_COVERAGE_MAX_AGE_DAYS`) it returns `none` without a model call. It and the classifier run at temperature 0 (`DECISION_CONFIG`).
  - `build_news_context` (formerly `formatted_prompting`) — first call (Phase 1): always returns the top Run of Play chunks from `kb_search.hybrid_search` (searched with the classifier's query plus the user's own question), labeled by age (`RUN OF PLAY CONTEXT` within 30 days, `RUN OF PLAY ARCHIVE ... background only` beyond), with the classifier's `search_required` (whether they're enough is `judge_kb_coverage`'s call); for latest-news questions newest first. `order_context` puts the combined answer's context in priority order: recent Run of Play articles, then the web results, then the archive (it used to put the archive before the web news); every answer turn says the material is in priority order. Second call (Phase 2, Phase 1's context passed in): web search via a self-hosted SearXNG instance (`SEARXNG_URL` env var, `engines=bing news`, `time_range=month` for latest-news questions — see below), checks `robots.txt` for the first 3 results in parallel and fetches them together in one browser (`crawl4AI.crawl_pages`, 5s deadline), keeps up to 2 as BM25-ranked chunks, and adds Bing's headline + snippet for up to 4 more, including pages that block the scraper. Sites that always serve anti-bot walls (`SCRAPE_BLOCKED_DOMAINS`: MSN, NYT, The Sun) go straight to snippets. American football never gets through: the query sent to Bing News names soccer (`_soccer_search_query`: "fantasy football" -> Fantasy Premier League; a "football" query naming no competition, club or player from Run of Play's tags gets "Premier League" in its place), a flash-lite check (`_keep_soccer_results`, `prompt_templates.build_soccer_results_prompt`) keeps only results about association football (if it fails, only results that name soccer outright), and the `AMERICAN_FOOTBALL` word filter drops results and scraped paragraphs first. ISO dates the classifier put in the query are stripped before searching. Next-match questions (`_is_fixture_question`: upcoming, next match, fixture, predicted XI, line-up, team news, preview..., unless a past year is named) search `<club> preview predicted lineup` (`_fixture_search_query`) over the last week and keep only results from the last `FIXTURE_MAX_AGE_DAYS` (3); `judge_kb_coverage` returns `none` for them without a model call unless a Run of Play article is that recent. Always returns `(context, search_required, formatted_query)`.
- `kb_search.py` — hybrid search over the Run of Play chunks: Pinecone cosine (top 30) + BM25 over every chunk (top 30, title and Wix tag words counted double, stemmed and accent-folded, unknown query words fuzzy-matched to the closest indexed word with the same first letter) + query-word coverage + exponential recency decay, fused per chunk (dense and BM25 min-max normalised across candidates). Keyword-only hits get their real cosine from their fetched Pinecone vectors. Weights per question type: latest-news 0.30/0.20/0.10/0.40 (recency half-life 30 days), otherwise 0.45/0.25/0.15/0.15 (half-life 365 days). Max 2 chunks per article. Words naming a club, player or competition (`_Snapshot.subject_terms`: a Wix tag spelled out in full, or a rare word found in a tag or two) are the question's subject: recent chunks about it always join the candidates, a chunk's score falls by up to half as its title and tags name less of it, and a new article about someone else is labeled background (`on_subject`). The BM25 index is a snapshot of every chunk's metadata and extracted facts, loaded from the knowledge store (`kb_store.py`); before a store exists it's built from the Wix blog without facts (`ingest_kb.wix_chunk_records`, the same ids and fields ingestion stores in Pinecone; ~15s, 1,773 chunks) in a background thread, started by `run.py` at startup and refreshed every 6h, with a copy on disk (`KB_SNAPSHOT_CACHE`, default `.cache/kb_snapshot.json`, ~3MB) that serves restarts within those 6h; a search that arrives first waits up to 20s for it, then ranks Pinecone's candidates alone. It is never read back from Pinecone (that used up the 1GB monthly read allowance). Every Pinecone call has a 2s deadline; after a quota error Pinecone is skipped for an hour (a minute after a timeout), and only the 10 best keyword-only candidates get their vectors fetched. `run.py` calls `kb_search.start_up()`: the keyword index, the embedding model and the Pinecone connection load in the background at startup. Logs every pick's signals as `[OffTheBar kb] ...`.
- `kb_google.py` — Pinecone-backed knowledge base. Embeddings computed locally with `fastembed` (ONNX build of `BAAI/bge-small-en-v1.5`, the same model the index was built with; no API key), index name `football-docs`. Exposes `embed_texts`/`get_pinecone_index` as public entry points (used by `ingest_kb.py`) alongside `search_pinecone` (used by the live retrieval path).
- `kb_store.py` — the knowledge store: one gzipped JSON with every chunk's metadata, a content hash, whether its vector is in Pinecone, and the facts gemini-2.5-flash-lite extracted from it at ingestion (`lasting_facts`, `time_bound_facts`, `scheduled_events`, `opinions`). In Cloud Storage in production (`KB_STORE=gs://runofplay-offthebar-kb/kb_store.json.gz`), `.cache/kb_store.json.gz` locally. `ragwithsearch._format_kb_hit` gives the answer model an ARCHIVE chunk's facts - time-bound ones marked "true as of <date> - may have changed since" - instead of its text, which states old clubs and form in the present tense. Recent chunks (30 days or less) keep their text, followed by their time-bound facts with the same marking.
- `football_data.py` — current facts from football-data.org's free plan: tables, recent and coming matches, squads, managers and top scorers for 10 competitions, in one gzipped JSON (`FOOTBALL_DATA_STORE`), written every 6 hours by the `offthebar-football-data` job. `context_for()` gives an answer the facts on the clubs, competitions and players a question names; `server/backend.py` (`with_football_data`) puts them first in every answer's context. `can_answer()` picks the table, fixture, result, manager and squad questions the data answers alone: those skip the web search, the coverage check and the source links, and a table question gets the table built in code (`table_markdown`) before the model's comment. FA Cup, Carabao Cup, Europa League and ISL aren't covered.
- `answer_check.py` — a last check in plain code as an answer streams, one sentence at a time (`server/backend.py`, `checked_text`). Invented credits ("The Run of Play's partners") are rewritten and sentences about the material dropped on every answer; on answers built on search results, a first name the material doesn't have is cut back to the surname, and a sentence naming someone it doesn't mention at all is dropped. It looks at names only, never numbers.
- `ingest_kb.py` — ingestion pipeline (`chunk_records` / `wix_chunk_records` are also what `kb_search` builds its keyword index from without a store). Incremental: only posts with a new or edited chunk (by hash), or a chunk missing its vector or facts, are embedded, upserted and sent for facts (`extract_facts`, one flash-lite call per post, `prompt_templates.build_chunk_facts_prompt`); removed chunks are deleted from Pinecone; `--assume-embedded` for a first run while Pinecone is already current. It used to re-embed every post daily. pulls posts from the Wix blog's REST API (`GET https://www.wixapis.com/v3/posts`, `fieldsets=CONTENT_TEXT` for plain text), chunks each post, embeds each chunk with the post title in front via `kb_google.embed_texts`, stores the title and tag labels (`list_wix_tags`, `GET /v3/tags`) in each vector's metadata, and upserts into Pinecone via `kb_google.get_pinecone_index`. Runs daily as the `offthebar-ingest-kb` Cloud Run Job (see `CLOUDRUN.md`), not as part of the request path.
- `prompt_templates.py` — full answers (complete-context and Phase 2) end with their follow-up prompts in a fixed `Ask next:` + list block (`FOLLOW_UP_FORMAT`); the clients cut it from the text and show the items as buttons that send the question. Also: system prompt (football-pundit persona, "controlled poetic flair" rules) and prompt builders for first draft / refinement / search classification.
- `gemini_utils.py` — every Gemini call goes through `call_gemini_with_key_retry()`. Keys (`GEMINI_API_KEY`, `GEMINI_API_KEY_2`, ... or `GEMINI_API_KEYS`) are tried in a fixed order, not round-robin: the free-tier keys named in `GEMINI_FREE_TIER_KEYS` (here `2`) first, then the paid ones (here `GEMINI_API_KEY`). A call moves on to the next key on quota exceeded, a bad/revoked key, or a server error (500/503 "overloaded", timeouts), but not on a 400. A key that hit a quota is skipped for that model until it should be back (daily quotas: midnight Pacific; rate limits: the `retryDelay` Gemini sends, else 60s); a bad key for an hour. Each call logs its key and token usage (`[OffTheBar Gemini] gemini-2.5-flash via key #1 (paid): input ..., output ..., thinking ... tokens`). Uses the `google.genai` SDK (`genai.Client`).
- `evals/` — pipeline evaluation framework (`evals/README.md`). `cases.json`: 51 dated questions in 9 domains (latest-news, match-results, awards, transfers, history, rules-tactics, gaming, conversation, robustness), each with optional expectations. `run_evals.py`: runs them through the real pipeline and scores every check into one of 7 weighted sections (understanding 15, retrieval 15, routing 15, answer accuracy 20, answer quality 15, safety & format 10, performance 10); routing sections by default (~$0.007), `--answers` adds real `/api/chat` answers for the 10 `core` cases, a flash-lite rubric judge and latency budgets (~₹2.5, less on fresh free quota), `--all-answers` every `answer` case (~₹5); the console and dashboard show both currencies, rate `USD_TO_INR` in `dashboard.py`. A case's answer runs first and its routing checks reuse that answer's search decision and coverage check (`Reused`). `scoring.py`: shared scoring (section = mean of its checks, overall = weighted mean of the sections that ran, domains likewise). `dashboard.py`: rebuilds the self-contained `evals/reports/dashboard.html` from every report (overall score + delta, run cost and cost per question in INR, section bars, score trend, domain × section heatmap, failed checks, case explorer, run selector and domain filter scoping everything below, light/dark, no page scroll at phone width). Reports are gitignored. Run it before deploys and after changes to retrieval, prompts or routing.
- `client/` — static frontend (`index.html`, `chat.js`, `style.css`) served by this Flask app at `/chat/`.
- `wix/` — the therunofplay.com chat page's code, which lives in the Wix editor: Velo page code (`offthebar-page.js`) and the two HTML embeds, `chatHtml` (`chat-iframe.html`) and `inputHtml` (`input-iframe.html`). The repo is the source of truth; changes only go live once pasted into the editor and published. Also the site-wide custom CSS (`global.css`, pasted into the editor's global CSS; the `fancyBox` / `fancyCircle` black-to-purple buttons) and `send-arrow.svg`, the home page's send-button arrow (white, transparent background, uploaded to Wix as Vector Art inside a `fancyCircle`). `wix/preview/` runs all three locally against a mock, local or live backend (`cd wix && python3 preview/serve.py`, a no-cache static server, open `http://localhost:8000/preview/`). `wix/README.md` covers the preview, publishing steps and the page ↔ embed message protocol.
- `Dockerfile` / `.dockerignore` — the Cloud Run image: Python 3.11-slim, Playwright/Chromium, NLTK `punkt`/`punkt_tab`, the embedding model baked into `/opt/fastembed` (`FASTEMBED_CACHE_PATH`), served by `gunicorn` (1 worker, 8 threads). `.dockerignore` keeps `.env` and `chat_logs/` out of the image.
- Config: `config.json` (host/port/proxy), `config_env.py` (`require_env` helper, loads `.env`), `.env.example` lists the env vars. On Cloud Run, secrets come from Secret Manager (`CLOUDRUN.md`); a `.env` file is only used for local dev and the legacy PythonAnywhere host (`PYTHONANYWHERE.md`).

## Known issues (verified 2026-10-30, not yet fixed)

- **Occasional cold instances.** `offthebar-api-keep-warm` keeps an instance up, but Cloud Run still replaces instances now and then; a question that reaches a cold one waits ~20s more. Before the keep-warm job, a tab left open past ~15 idle minutes, or an old page, hit this every time.
- **Misfiled facts, held for one re-extraction** (`FACTS_VERSION` bump, about ₹30 by the first full run). Career totals of active players are filed as lasting: "Cristiano Ronaldo played in 5 FIFA World Cups from 2006 to 2022" (November 2025) reached an October 2026 answer as current, after his sixth. Who holds a job ("Manuel Pellegrini is the manager of Real Betis") and finished-match stats filed as time-bound are the other known errors. The extraction prompt's lasting list says a finished tournament's numbers can't change, and nothing says a career total can.
- **Legacy PythonAnywhere may still expose `.env`.** The `/assets` path traversal (fixed in code on 2026-10-30, see Current progress) served repo-root files, and `PYTHONANYWHERE.md` puts `.env` in the repo root. That host still runs the old code; it was never tested against the live host. Take it down (or delete its `.env`), and rotate the keys if it turns out to have been reachable.
- **Open API, no limits.** Public Cloud Run invoker + CORS `*` + no credential check or rate limit. `--max-instances 2` is live, but a cap limits the spending rate, not the spending. When both instances are full, Cloud Run answers 429 or 503, probably without CORS headers, so `wix/offthebar-page.js` shows its "try again" message for those statuses and for a failed fetch (live once `wix/` is published). Never tested against a real full service. A two-phase answer costs ~2 `gemini-2.5-flash` calls against the free tier's ~20 requests/day per model per key, so anyone who finds the URL can exhaust the daily quota (and drive Cloud Run scaling). Also `payload["jailbreak"]` is a required key (`server/backend.py`) though it's only printed, so API callers that omit it get the generic error message.
- Smaller:
  - `FLASK_SECRET_KEY` is required at startup but nothing uses sessions any more, and `require_env(...) or os.urandom(32)` can never reach its fallback (`require_env` raises).
  - `requirements.txt` is unpinned (pinecone v10 already broke `upsert()` once), and `index.html` loads markdown-it and highlight.js `@latest` from the CDN.
